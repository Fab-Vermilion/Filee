# 失败清单最终复核报告（真实失败）

## 复核方法
对全量矩阵报告的 1190 条失败，逐层用**正确的输入和正确的引擎**重跑验证，剔除测试工具自身造成的假失败：

1. **第 1 层**：用内容完整的优质种子重跑 → 1074 条重试成功（原失败是测试种子内容/后缀问题）。剩 116 条。
2. **第 2 层**：发现复核工具未指向项目 engines/，实际用了系统 homebrew FFmpeg（缺 libtheora/libvorbis）。改为项目 engines/（b2g FFmpeg，编码器齐全）重跑 116 → 105 条成功。剩 11 条。
3. **第 3 层**：逐条分析 11 条——10 条是 `→ics`，失败原因是源数据不含日历字段（summary/begin 列）；用含日历列的 CSV 实测 `csv→ics` **成功**。剩 1 条。

## 最终结论：真正的失败只有 1 条

| 源格式 | 目标格式 | 错误 | 性质 |
|---|---|---|---|
| eml | zip | `no_route`（eml → zip 无转换路由）| ~~真能力缺口~~ **已从 Web 白名单剔除（已修）** |

`eml`（邮件）在 Web 白名单里被归为 Document 类，`zip` 是 Archive 类，因此 `/api/formats` 把 `eml → zip` 展示为可选项；但引擎实际没有这条路由，用户选中后必失败。）

## 附带发现

- 全量矩阵与第 1 层复核工具运行在 `/tmp`，未把 `EngineEnvironment.DownloadRoot` 指向项目 `engines/`，因此**全程使用了系统 homebrew FFmpeg**（缺 libtheora/libvorbis），导致 ogv/ogg/webp 大面积假失败。这解释了原报告里「编码器缺失 102 条」的来源。
- 真正的应用（WB 里运行）的 BaseDirectory 在项目 bin 目录，能正确找到 `engines/`，因此 ogv/ogg/webp 在应用中是正常的（已用项目 engines + 项目转换逻辑实测成功）。
- 原报告 `full-failures.tsv` 的 1190 条中，除 eml→zip 外均为测试工具造成的假失败；`ENCODER-MISSING.md` 的复核结论（编码器其实存在）在本报告进一步确认。

> **已修复（2026-11-18 07:03）**：按用户决定，从 Web 白名单剔除了 `eml→zip` 这条边——`FormatTargetCatalog` 新增边级黑名单 `BlockedEdges = {"eml=>zip"}`，`/api/formats` 不再向用户展示该选项；新增回归测试断言。其余 1189 条为测试工具假失败，无需修复。
